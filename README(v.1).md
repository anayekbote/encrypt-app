# Encrypt (v1.0.0)

Encrypt is an offline, zero-network authenticated encryption tool built with Flutter for Android and Windows. It provides authenticated symmetric encryption using **AES-256-GCM** and **PBKDF2-HMAC-SHA256**, enabling two parties to exchange tamper-proof messages over untrusted channels (SMS, email, instant messengers) using a pre-shared passphrase.

## Architectural Data Flow

The application executes strictly in local volatile heap memory without background processes, telemetric trackers, or remote network access.

```text
[ User Plaintext Input ] + [ Pre-Shared Passphrase ]
                      │
                      ▼
          [ PBKDF2-HMAC-SHA256 ]
     (Salt: Static, Iterations: 10,000)
                      │
                      ▼
        256-bit Symmetric Key (DK)
                      │
       ┌──────────────┴──────────────┐
       ▼                             ▼
[ AES-256-CTR ]               [ GHASH Engine ]
(Confidentiality)             (Integrity over GF(2¹²⁸))
 96-bit CSPRNG Nonce           128-bit MAC Tag
       │                             │
       ▼                             ▼
   Ciphertext                    Auth Tag
       │                             │
       └──────────────┬──────────────┘
                      ▼
[ Binary Packing: Nonce (12B) + Ciphertext (NB) + Tag (16B) ]
                      │
                      ▼
              [ Base64 Encoding ]
                      │
                      ▼
       Prefix: "ENCv1:<Base64Payload>"
```

## Cryptographic Specification & Mathematical Model

### 1. Key Derivation: PBKDF2-HMAC-SHA256 (RFC 2898)
To transform human-chosen passphrases into a uniformly distributed 256-bit key, Encrypt implements the Password-Based Key Derivation Function 2 (PBKDF2) using HMAC-SHA256 as the underlying pseudorandom function ($\text{PRF}$).

#### Mathematical Definition
Given:
* Passphrase: $P$
* Static Salt: $S = \text{utf8}(\text{"CryptoApp\_StaticSalt\_v1"})$
* Iteration Count: $c = 10{,}000$
* Output Length: $dkLen = 32\text{ bytes (256 bits)}$
* Hash Output Size: $hLen = 32\text{ bytes (256 bits)}$

Because $l = \lceil dkLen / hLen \rceil = 1$, the derived key $DK$ corresponds to a single 32-byte block $T_1$:

$$DK = T_1 = F(P, S, c, 1)$$

Where $F$ is calculated as the bitwise XOR sum of $c$ recursive HMAC passes:

$$F(P, S, c, 1) = \bigoplus_{k=1}^{c} U_k$$

$$U_1 = \text{HMAC-SHA256}(P, S \parallel \text{INT\_32\_BE}(1))$$
$$U_k = \text{HMAC-SHA256}(P, U_{k-1}) \quad \text{for } 2 \le k \le c$$

---

### 2. Authenticated Encryption: AES-256-GCM (NIST SP 800-38D)
Galois/Counter Mode (GCM) combines the Counter (CTR) mode of encryption for confidentiality with universal hashing over a binary Galois field ($GF(2^{128})$) for authentication.

#### A. Confidentiality (AES-256-CTR)
AES operates over $GF(2^8)$ on 128-bit state matrices using a 256-bit key derived via PBKDF2 through 14 transformation rounds.

1. **Nonce Generation:** A cryptographically secure random 96-bit (12-byte) initialization vector is generated per operation from the host operating system's CSPRNG:
   $$IV \in \{0, 1\}^{96}$$

2. **Counter Initialization:** Since $\vert{}IV\vert{} = 96\text{ bits}$, the initial counter block $J_0$ is generated by appending 31 zero bits and a single one bit:
   $$J_0 = IV \parallel 0^{31}1$$

3. **Keystream Transformation:** Plaintext blocks $P_1, P_2, \dots, P_n$ are XORed against the encrypted counter blocks:
   $$J_i = \text{incr}_{32}(J_{i-1}) \quad \text{for } i \ge 1$$
   $$C_i = P_i \oplus \text{AES}_{DK}(J_i)$$

Because encryption is executed as a bitwise stream operation, no PKCS#7 padding is added; the ciphertext bit length matches the plaintext bit length precisely.

#### B. Integrity & Authenticity (GHASH over $GF(2^{128})$)
To detect any ciphertext manipulation or bit-flipping:

1. **Hash Subkey:** Computed by encrypting an all-zero 128-bit block with the derived key:
   $$H = \text{AES}_{DK}(0^{128})$$

2. **Galois Field Definition:** Arithmetic is computed modulo the irreducible field polynomial:
   $$f(x) = x^{128} + x^7 + x^2 + x + 1$$

3. **GHASH Formulation:** Ciphertext blocks $C_1, \dots, C_m$ are evaluated using Horner's rule:
   $$Y_0 = 0^{128}$$
   $$Y_i = (Y_{i-1} \oplus C_i) \cdot H \quad \text{for } i = 1, \dots, m$$
   $$Y_{m+1} = (Y_m \oplus (0^{64} \parallel \text{len}(C)_{64})) \cdot H$$

4. **Tag Generation:** The 128-bit authentication tag $T$ is masked via $J_0$:
   $$T = Y_{m+1} \oplus \text{AES}_{DK}(J_0)$$

## Wire Format Specification

Encrypted outputs are serialized into a single ASCII-safe string prefixed with `ENCv1:`:

```text
ENCv1:<Base64( ) Auth Bytes] Ciphertext Nonce Tag [12 [16 [N ||>
```

### Binary Frame Layout

```text
 0                   11 12                   N+11 N+12                N+27
+----------------------+-------------------------+------------------------+
|   Nonce (12 Bytes)   |   Ciphertext (N Bytes)  |   Auth Tag (16 Bytes)  |
+----------------------+-------------------------+------------------------+
 \____________________/ \_______________________/ \______________________/
       IV (96-bit)         Encrypted Message       GHASH Verification Tag
```

### Decryption Invariants
- Minimum valid binary payload size is **28 bytes** (12-byte Nonce + 0-byte Ciphertext + 16-byte Tag).
- Any payload lacking the `ENCv1:` prefix or failing Base64 decoding is immediately rejected.
- If $T' \neq T$, the cryptographic engine throws an authentication failure; **zero plaintext bytes are emitted**.

## Security Model & Limitations

While ENCv1 guarantees IND-CCA2 security when used with unique, random passphrases, users and developers must evaluate the following inherent architectural limitations:

1. **Symmetric Shared-Secret Bottleneck:**
   - Both parties must negotiate and share the identical passphrase out-of-band.
   - If the passphrase is transmitted over an unencrypted channel (such as cleartext SMS or unencrypted email), the security of all associated messages is compromised.

2. **Static Salt Vulnerability:**
   - ENCv1 utilizes an application-wide static salt (`CryptoApp_StaticSalt_v1`).
   - While this prevents cross-application precomputation attacks, it allows an adversary targeting this application to construct targeted rainbow tables or perform simultaneous multi-user dictionary attacks for common passphrases.

3. **PBKDF2 Work Factor Constraints:**
   - 10,000 iterations of PBKDF2-HMAC-SHA256 was selected to balance low latency on resource-constrained mobile hardware with brute-force resistance.
   - Modern GPU clusters and custom ASIC arrays can compute millions of PBKDF2 hashes per second. Short, dictionary-based passphrases can be cracked rapidly if an encrypted payload is intercepted.

4. **Absence of Replay Protection:**
   - ENCv1 payloads do not contain cryptographic timestamps, sequence counters, or recipient identifiers.
   - An attacker capable of intercepting traffic cannot read or alter the message, but they can re-transmit (replay) valid historical payloads to trigger repeated actions.

5. **Local Host & Memory Exposure:**
   - Keys and plaintexts remain in volatile application memory while processing.
   - Operating system clipboard loggers, cloud clipboard synchronization tools, and memory dumps can capture sensitive strings if the host device itself is compromised.
